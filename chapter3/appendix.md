# 第 3 章付録

## Git の基本概念

Git における主要な概念や操作について簡単に説明します。
Git には非常に多くのコマンドやオプションがありますが、ここではハンズオンで必要なごく一部の操作のみ説明します。
Git について解説した良書や Web サイトが多数ありますので、是非参照してください。

Git により、あるディレクトリ配下にあるファイルの変更履歴（バージョン）を管理できます。
ローカル環境にあるディレクトリで Git によるバージョン管理を有効化するためには、コマンド `git init` を実行します。

```sh
git init
```

これによりディレクトリ直下に `.git` というディレクトリが作成され、そこにバージョン管理に関する情報が保存されます。
Git によるバージョン管理を有効化したディレクトリを Git リポジトリと呼びます。

Git ではコミットと呼ばれる単位でファイルの変更を管理します。
コミットには Git リポジトリ配下にあるファイルのその時点での状態が保存されます。
Git であるファイルの変更履歴を管理するためには、一度ファイルを含むコミットを作成する（コミットする）必要があります。

初めてコミットを作成する前に、コミット作成者の名前やメールアドレスをコマンド `git config` で設定する必要があります。

```sh
git config user.name "<名前>"
git config user.email "<メールアドレス>"
```

コミットを作成するためには、コミットの対象とする変更内容を選択します。
この操作をステージングと呼び、コマンド `git add` で実行します。

```sh
# カレントディレクトリ以下の全てのファイルをステージングする
git add .
```

ステージングにより、コミットに含めたい変更だけを選択的に指定できます。

なお、`.gitignore` という名前のテキストファイルを作成することで、Git の管理対象から除外したいファイルやディレクトリを指定できます。
`.gitignore` にファイル名やパターン（例: `*.log`）を記述すると、それらに一致するファイルは `git add` を実行してもステージングされません。

ステージングが完了したら、コマンド `git commit` によりステージングされた内容をコミットします。
オプション `-m` でコミットメッセージを挿入して、コミットの内容を説明します。

```sh
git commit -m "初めてのコミット"
```

最初のコミットが完了すると、デフォルトブランチ（通常は `main` または `master` という名前）が自動的に作成されます。
ブランチとは、異なるコミット履歴を並列して管理するための機能です。
ブランチは複数作成することができ、それぞれのブランチにコミットを追加することができます。
デフォルトブランチ以外は、あるブランチから分岐する形で作成します。
ブランチを切り替えるにはコマンド `git switch` を実行します。

```sh
# feature/dbt という名前のブランチを作成し、そのブランチに切り替えます。
git switch -c feature/dbt

# すでに存在するブランチに切り替える場合は、オプション -c は不要です。
git switch feature/dbt
```

あるブランチで管理するコミット履歴を、異なるブランチに反映することもできます。
この操作をマージと呼び、コマンド `git merge` で実行します。

```sh
# 選択中のブランチ（main など）にブランチ feature/dbt をマージする
git merge feature/dbt
```

Git リポジトリをチームで共有する場合、ブランチとマージの機能を活用することで、並行して異なる編集作業を進めることができます。
多くの場合、デフォルトで作成される `main` ブランチではなく、用途に応じたブランチを作成しファイルを編集するのが一般的です。
異なるブランチを利用して開発を進め、一区切りついたところで大元のブランチにマージすることで、開発した実装を取り込みます。
`main` ブランチの役割はプロジェクトにより異なりますが、本番環境と同じソースコードを保管するなど重要なブランチとして扱われることが多いです。
ブランチの管理・運用は CI/CD においては重要なトピックなので、後ほど改めて説明します。

ソースコードをチームで共有する・バックアップするなどの目的で、ローカル端末だけではなくサーバー上にも Git リポジトリを保存するのが一般的です。
サーバー上で保管され、複数人で共有可能な Git リポジトリをリモートリポジトリと呼びます。
一方、ローカル端末に保存された Git リポジトリをローカルリポジトリと呼びます。
リモートリポジトリを管理するためのサービスとして GitHub や GitLab などがありますが、本書では GitHub を利用します。

ローカルリポジトリで作成したブランチやコミットをリモートリポジトリに送信して更新することができます。
この操作をプッシュと呼び、コマンド `git push` で実行できます。
ただし、プッシュする前にローカルリポジトリでリモートリポジトリを登録する必要があります。
一般的には `origin` という名前でリモートリポジトリを登録します。

```sh
git remote add origin "<リモートリポジトリの URL>"
```

リモートリポジトリの登録が完了したら、ブランチとそのコミット履歴をリモートリポジトリにプッシュできます。

```sh
git push -u origin main
```

リモートリポジトリの変更内容をローカルリポジトリに反映することもできます。
コマンド `git pull` を利用するのが簡単です。
例えば、リモートリポジトリの最新状態を取得し、リモートリポジトリのブランチ `main` をローカルリポジトリおける現在のブランチにマージするためには、以下のコマンドを実行します。

```sh
git pull origin main
```

チーム開発では、新規のチームメンバーはリモートリポジトリをローカル端末にコピーすることから始めます。
リモートリポジトリの最新状態を取得しローカルリポジトリを作成するためには、コマンド `git clone` を実行します。

```sh
git clone "<リモートリポジトリの URL>"
```

## GitHub の基本機能

GitHub はリモートリポジトリを管理するためのサービスであり、ソフトウェア開発のプラットフォームとして広く利用されています。
GitHub では多数のオープンソースソフトウェア（OSS）が管理・公開されていますが、プライベートな個人開発やチーム開発でもよく利用されます。

GitHub の機能は非常に豊富ですが、本章のハンズオンでは以下の機能を利用します。

- プルリクエスト
- プライベートリポジトリ
- GitHub CLI
- GitHub Actions

プルリクエストは、ブランチをマージする前に、レビューや CI パイプラインなどを実行するための機能です。
開発者が GitHub のリモートリポジトリにブランチをプッシュした後、プルリクエストを作成することで、GitHub 上で変更内容を確認できます。
プルリクエストにおいて、変更内容に関してチームメンバーがコメントしたり、マージを承認したりできます。
プルリクエストを作成した後にコードレビューをするのが一般的であり、プルリクエストはチーム開発で欠かせない機能のひとつです。
また、プルリクエストを作成することで CI パイプラインなどを自動的に開始することも可能なため、マージする前に問題がないか自動的に確認する仕組みも作れます。

プライベートリポジトリとは、個人または一部のユーザーのみがアクセスできる非公開の GitHub リポジトリ（GitHub で管理されるリモートリポジトリ）のことです。
一方、OSS が管理されるリポジトリなど、公開されている GitHub リポジトリをパブリックリポジトリと呼びます。
ハンズオンでは、セキュリティを考慮しプライベートリポジトリを利用します。
パブリックリポジトリを利用しても問題ないよう配慮していますが、パブリックリポジトリは任意のユーザーが閲覧できるため、ファイルにアクセスキーなどの機密情報が混入しないよう十分注意してください。

GitHub CLI とは、ターミナル上で GitHub での操作を実行するためのコマンドラインツールです。
GitHub が公式に提供しています。
GitHub での操作は、慣れないうちはブラウザなど GUI の方がわかりやすいですが、ハンズオンでは基本的に GitHub CLI を利用します。
GitHub CLI を利用することで、ターミナル上での操作を中断することなく GitHub を操作できるためです。
ハンズオンで実行する GitHub CLI のコマンドについては、その都度簡単に説明しますが、詳しい構文やオプションは適宜 GitHub CLI の公式ドキュメント [^github_cli_manual] などを参照してください。
本章のハンズオンで登場する主な GitHub CLI コマンドを以下に示します。

[^github_cli_manual]: https://cli.github.com/manual/

- `gh auth login`：GitHub CLI で GitHub にログイン（認証）する
- `gh repo create`：リモートリポジトリを作成する
- `gh secret set`：GitHub シークレットを設定する
- `gh pr create`：プルリクエストを作成する
- `gh run list` / `gh run watch`：ワークフロー実行の一覧表示と経過の監視を行う
- `gh workflow run`：ワークフローを手動で起動する

GitHub Actions とは、CI/CD パイプラインを実行するための機能です。
GitHub Actions を利用することで、GitHub リポジトリで管理されるソースコードに対しテストやビルドなどを実行するパイプライン（ワークフロー）を自動的に実行できます。
パイプラインはプルリクエストの作成などをトリガーとして開始されます。
パイプラインの実行環境は、基本的に GitHub がクラウド上で提供するため、ユーザーがサーバーなどを準備する必要はありません。
GitHub Actions の利用方法などについては、後ほど改めて説明します。

ここで紹介した GitHub の機能は、基本的に無料で利用できます。
無料プランでは、GitHub Actions でのワークフロー実行時間などの制約がいくつかありますが、本章のハンズオンを進める上では無料プランで問題ありません。

## GitHub Actions と AWS との連携

GitHub Actions のランナーから AWS に接続する方法について説明します。

AWS に接続するためには、ランナー上で AWS の認証情報を設定する必要があります。
認証情報を設定するために、アクション `aws-actions/configure-aws-credentials` を実行するのが一般的です。

アクション `aws-actions/configure-aws-credentials` では認証情報の設定方法をいくつか選べますが、OpenID Connect（OIDC）という仕組みを利用することが推奨されます [^openid_connect_aws] 。
OIDC を利用すると、ジョブを実行する毎に一時的な認証情報を都度取得することができ、シークレットアクセスキーなどの認証情報を長期保存する必要がありません。
ここでは OIDC に関する説明は割愛しますが、興味のある方は Web の解説記事 [^id_token_openid_connect] をご参照ください。

[^openid_connect_aws]: https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws

[^id_token_openid_connect]: https://qiita.com/TakahikoKawasaki/items/8f0e422c7edd2d220e06

アクション `aws-actions/configure-aws-credentials` で OIDC を利用する場合、自動的に以下の手順で認証情報が取得されます。

1. ワークフローのジョブ実行時に、GitHub OIDC プロバイダーに対し OIDC トークンを要求します。
2. GitHub OIDC プロバイダーがユニークな OIDC トークンを発行します。
3. アクション実行時に、引き受ける IAM ロールの ARN などの情報と OIDC トークンを AWS に送信します。
4. AWS は OIDC トークンを検証し、IAM ロールの一時的な認証情報を発行します。

OIDC トークンは、ジョブを実行するリポジトリやブランチなどの情報や、それらの情報に対する署名から構成されます。
AWS は OIDC トークンに含まれる署名を検証することで、リポジトリやブランチなどの情報が正しいことを確認します。
また、IAM ロールの信頼ポリシーで、IAM ロールの引き受けを許可するリポジトリなどを設定できます。
よって、リポジトリ内のワークフローに対してのみ、安全に一時的な認証情報を発行できます。

OIDC を利用するために、AWS アカウントでは、IAM ロールの他に IAM OIDC プロバイダーをあらかじめ作成します。
IAM OIDC プロバイダーは、GitHub の OIDC トークンを検証して認証情報を発行するために、必要なリソースです。
IAM ロールや IAM OIDC プロバイダーの設定については、資料 [^openid_connect_aws] を参照してください。

ワークフローファイルのサンプルとして、GitHub リポジトリのファイルを S3 にアップロードする例を示します。

```yml
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  upload_file:
    runs-on: ubuntu-latest
    steps:
      - name: チェックアウト
        uses: actions/checkout@v6

      - name: 一時認証情報を設定
        uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: <IAM ロールの ARN>
          aws-region: ap-northeast-1

      - name: ファイルを S3 にアップロード
        run: aws s3 cp hello_world.txt s3://<S3 バケット名>/
```

アクション `aws-actions/configure-aws-credentials` では `role-to-assume` と `aws-region` の 2 つのパラメータが必要です。
`role-to-assume` で設定した IAM ロールを引き受けることで、その IAM ロールに許可されたアクションを実行できるようになります。
また、ワークフローが OIDC トークンを取得するために、パーミッション `id-token: write` の設定も必要です。
